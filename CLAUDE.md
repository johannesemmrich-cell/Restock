# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build

```bash
# Build for simulator (no sudo needed after first setup)
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  xcodebuild -scheme Restock \
             -project Restock.xcodeproj \
             -destination 'generic/platform=iOS Simulator' \
             build 2>&1 | grep -E "error:|BUILD SUCCEEDED|BUILD FAILED"
```

The `Restock` scheme's Test Action pins `language="de"` / `region="DE"`, so UI tests always run in German regardless of the simulator's system language — relevant because the CI runner defaults to English. The tests assert on German label text, so this override is what makes them pass there; passing an explicit `-testLanguage`/`-testRegion` on the command line still overrides the scheme setting. `scripts/verify-ui-test-language.sh` proves this on a freshly erased, English-language simulator: one run without a language flag (expected 0 failures) and one with `-testLanguage en -testRegion US` as a negative control (expected the three known failures). Because the UI tests key off displayed text rather than `accessibilityIdentifier`s in the product code, copy changes can break them.

Some UI tests need a fixture screen that's normally only reachable via camera/OCR; these use DEBUG-only launch arguments in `SmartCartApp.swift` to seed the required data directly through the app's real data path. Because the app-group container persists across tests in the same `xcodebuild test` run, every test class that seeds data this way **must** remove it again in `tearDown()` via its own matching cleanup launch argument — otherwise leftover stores/items break other tests' assumptions, since the existing suite does not reset its own state.

## Adding new Swift files

Xcode does **not** auto-discover files on disk. Every new `.swift` file must be manually registered in `Restock.xcodeproj/project.pbxproj` in three places:

1. `PBXBuildFile` — links build UUID → file reference UUID
2. `PBXFileReference` — declares the file path
3. `PBXGroup` child list — places it in the correct folder group
4. `PBXSourcesBuildPhase` — adds it to the compile sources

Use 24-character hex UUIDs that don't conflict with existing ones. Use the `general-purpose` agent to do this reliably (it can read and edit pbxproj without external tools).

## Architecture

**iOS 18+, Swift 5.9, SwiftUI + SwiftData. No third-party dependencies.**

### Data layer — SwiftData models (`SmartCart/Models/`)

| Model | Role |
|-------|------|
| `Store` | A shop (name, emoji, color, visit frequency, learned item order). Owns `ShoppingItem`s. |
| `ShoppingItem` | One item on a list. Belongs to a `Store`. On completion, creates a `PurchaseRecord`. |
| `PurchaseRecord` | Historical log of a completed purchase. Powers habit/frequency analysis. |
| `FeedbackItem` | Dev-mode feedback entry (context, text, priority, isResolved). SwiftData only. |
| `TodoItem` | Dev-mode todo/idea. SwiftData only. |

`ModelContainer` is created in `SmartCartApp.init()` with all five models. **When adding a new `@Model`, it must be added to the `ModelContainer` initializer.**

`Store.learnedPriceUnits` (Issue #10) is a parallel map to `Store.learnedPrices`, keyed the same way, holding the bucket the price was learned in (`"stk"` for a piece price, `"g"` for a weight/volume subunit — g, mg, ml, cl, dl are collapsed, see `ShoppingItem.unitBucket`). A `learnedPrices` entry with no matching `learnedPriceUnits` entry is legacy data and is never applied. `ShoppingItem.init` looks up `unitBucket(item.unit)` against the learned bucket and a `learnedRateUsage` decision table (top of `ShoppingItem.swift`) picks apply / rate-only / reject — a gram rate is never silently multiplied onto a quantity-less item as if it were a piece price. `ShoppingItem.quantitySource` (`"user"`/`"history"`/`"package"`/`"none"`) records where the item's quantity came from; `AssignmentService.suggestQuantity(itemName:storeName:purchaseRecords:)` (Issue #57) is what sets it in `AddItemView` — last purchase of the same item at the same store, else a package size parsed from the typed name (`ReceiptParserService.packageSizeFromName`), else `"none"`. It re-runs on every name change unless `quantityTouchedByUser` is already `true` (flipped once by the computed `userQuantity`/`userUnit` bindings the moment the user edits quantity or unit themselves), so a stale suggestion from an intermediate name doesn't stick and a manually typed value is never overwritten regardless of edit order. `ItemRow`'s `"ca. "`-prefixed, tinted quantity line for `"history"`/`"package"` and `EditItemView`'s reset to `"user"` on manual correction (both pre-existing from Issue #10) are reachable now; `ItemRow`'s price cell additionally falls back to a per-100g rate instead of a fabricated total when `quantitySource == "none"`. `LegacyLearnedPriceReset` (Issue #11, einmalig per `legacyLearnedPriceResetV1Applied`, läuft in `SmartCartApp` direkt nach `PriceProvenanceMigration`) setzt Artikelpreise, die dem Altwert eines `learnedPrices`-Eintrags ohne `learnedPriceUnits` entsprechen, auf die Katalogschätzung zurück; die Namenszuordnung teilt es sich über `ShoppingItem.matchingLearnedPriceKey` mit `ShoppingItem.init`. Details: `docs/specs/models/legacy-price-reset-migration.md`. Details: `docs/specs/models/learned-price-unit-and-quantity-source.md`, `docs/specs/services/assignment-service-quantity-suggestion.md`.

### Services (`SmartCart/Services/`)

- **`AssignmentService`** — assigns a new item to the best `Store` based on: (1) purchase history dominance, (2) drugstore-keyword matching, (3) highest-visit grocery store. Also maps item names → category strings. `suggestQuantity(itemName:storeName:purchaseRecords:)` (Issue #57) is a separate pure function proposing a quantity/unit/`quantitySource` for a new item without one — see `quantitySource` above. `assignDetailed(itemName:to:purchaseRecords:)` is the same decision as `assign` plus an `AssignmentReason` (user correction / purchase counts / default store / only matching store / most visited / no store for a group) that the quick-add target card shows as a sentence; `assign` just returns its `store`. A default store chosen in Settings → Standard-Läden (`DefaultStoreService`) is looked up among ALL active stores, not only those whose `categories` match the group, and wins before the history/visit heuristic (but not before an explicit per-item correction or a dominant purchase history).
- **`QuickAddParser`** — parses freetext like `"500 gramm Hackfleisch"` → `{name, quantity, quantityAmount, unit}`. `knownUnits` contains both abbreviations (`g`, `kg`) and German long-forms (`gramm`, `kilogramm`, etc.).
- **`HabitService`** — reads `PurchaseRecord`s, calls `consumptionPattern()` on each group, returns items due for repurchase. IQR outlier filtering in `PurchaseRecord.swift` removes vacation gaps from interval averages. The interval is not scaled by purchase quantity (Issue #30, A1). `ShoppingItem.markPending()` deletes the `PurchaseRecord` its `markCompleted()` created unless a receipt price was attached (A2). `OverdueNotificationLedger` limits the immediate overdue push to once per item and purchase cycle (A3); `ReplenishmentFeedback.resolveAccepted` (called from `HomeView.refreshDueSoon()`) treats a banner suggestion that was added and then deleted without a purchase like a ✕ dismissal (A4). Package B/D: `consumptionPattern()` collapses same-day purchases (B6), uses a recency-weighted interval (B1) and a consumption rate when all purchases share a unit (B5), switches to a weekday mode for items bought on fixed weekdays such as Mo + Mi (`PurchaseDay.fixedWeekdays`, 4a), and moves a date on a Sunday/German public holiday to the day before via `RetailClosedDays` (4b; default `.none`, `HabitService` passes `.current`). `HabitService.ineligibility` enforces ≥3 purchase days, coefficient of variation ≤ 0.5 in interval mode (measured on the consumption rates when B5 applies, else on the intervals), and ends a habit after 2.5× the typical gap (B2/B4); `ConsumptionPattern.dueWindowDays` is 20 % of the cycle, clamped to 1…7 days (B3). `HabitService.backtest` and `ReplenishmentMetrics` feed the dev-mode `ReplenishmentStatsView` (Settings → Nachkauf-Statistik, D1). C1: the banner's ✕ is a menu — „Hab noch“ (`ReplenishmentSnoozes`, shifts the date by half the usual gap, 1…14 days, but always at least due window + 2 days after now so it never reappears immediately, until the next purchase; the pattern keeps the computed date in `originalEstimatedDate`) and „Nicht mehr vorschlagen“ (`ReplenishmentBlocklist`); both are passed to `HabitService.dueSoonItems(from:snoozes:blocked:)` and can be undone in Settings → Developer → Ausgeblendete Vorschläge (`HiddenReplenishmentsView`). A3, A4, C1 and the D1 „shown“ count identify a purchase cycle by `ConsumptionPattern.purchaseKey` (timestamp of the latest `PurchaseRecord`), never by the computed date, which shifts with country (4b) and time zone without a purchase; `ReplenishmentKeyMigration` converted the older date-keyed entries once. C4: `HabitService.dueBeforeNextVisit` feeds the dev-mode section „Vielleicht auch fällig“ in `StoreDetailView` — items `AssignmentService.assign` puts into this store that are in the banner window or run out before the next visit (now + `StoreVisitForecast.visitGapDays`: median gap of the store's last 8 visit days from `PurchaseRecord.storeName`, ≥ 3 days, else `7 / visitsPerWeek`, clamped to 1…28), with the banner's filters; „Hab noch“ there snoozes at least until that next visit (`snooze(notBefore:)`). C5: records are grouped per item by `ReplenishmentItemIdentity` (top of `HabitService.swift`) — only user-confirmed receipt aliases (`ReceiptAliasService`) and purely formal differences (case, extra spaces, punctuation at the edges, `formalKey`) are merged; never fuzzy, AI, prefix or stem matching („Milch“ ≠ „H-Milch“ ≠ „Hafermilch“). All stored replenishment entries and pending-item checks use `ConsumptionPattern.itemKey` / `identity.key(_:)` instead of `lowercased()`.
- **`SeasonalService`** — returns seasonal suggestions per month. Controlled by `@AppStorage("seasonalSuggestionsEnabled")`.
- **`RecipeRecognitionService`** — Vision OCR + Apple Intelligence (`FoundationModels`, iOS 26+) to extract ingredients from a photo.
- **`ReceiptParserService`** — parses receipt lines (Vision OCR/PDF) into `ReceiptLine`s (name, price, `quantity`, `weightBasis`). Two formats (`parseClassic` with VAT suffix, `parseEuroSuffixStyle`); quantity/weight confirmation lines under an item line are attributed to the preceding line (sanity check, Issue #9), never created as their own position; one directly following a STORNO line is skipped instead, without consuming `pendingStornoCancel` (Issue #24). Eine Zeile `[Artikelnummer] Preis[€|EUR]` direkt unter einer Namenszeile ist deren Preis (Decathlon-PDF, `articleNumberPriceRegex`, PR #199); Tabulatoren zählen als Spaltenlücke. Gleichnamige Positionen werden in `dedupAndSort` addiert (Menge und Preis: zweimal 8,99 € → 2 St., 17,98 €), nicht mehr überschrieben (PO 2026-10-21). Test: `ReceiptParserDecathlonTests`.
- **`ReceiptNameAIResolver`** (Stufe 5 der Bon-Namensauflösung, `ReceiptParserService.swift`) — das Modell steckt hinter `ReceiptNameLanguageModel` (produktiv `SystemReceiptNameLanguageModel`), `ReceiptResolutionService.resolve(…, aiResolver:)` nimmt einen Resolver mit Schein-Modell. Nachprüfung: Kürzel-Antworten („Bröt.“) verworfen, Kürzel nicht im Prompt-Kontext, dieselbe Antwort für ≥ 3 fremde Zeilen ohne Wortbezug verworfen (`discardingRepeatedUnrelatedAnswers`). Tests: `ReceiptAIResolutionChainTests` (K1–K7, ganze Kette mit Schein-Modell), `ReceiptNameAIResolverSanitizeTests`. Beim Speichern lernt `save()` keinen Alias auf ein Kürzel-Ziel (`ReceiptAliasService.isLearnableTarget`) und keinen für Namen an ≥ 3 fremden Zeilen (`ReceiptLearning.aliasLearnableIndices`); `AbbreviatedNameCleanup` (einmalig, `abbreviatedNameCleanupV1Applied`, in `SmartCartApp` nach `LegacyLearnedPriceReset`) entfernt Aliase mit Kürzel-Ziel, gelernte Preise unter Kürzel-Schlüsseln und Kaufdatensätze nur im Fehlermuster (Kürzel-Name mit Bon-Preis, ≥ 3 am selben Tag im selben Laden, `bugPatternRecords`). Offene Grenze: das echte Modell ist in CI/Simulator nicht prüfbar. Details: `docs/specs/fast/fix-ai-receipt-name-broet.md`. Messung mit dem echten Modell (Issue #159): `RestockTests/ReceiptNameAIEvaluationTests.swift` (ganz in `#if AI_EVAL`, sonst leer; dm-, Lidl-, Rewe-Zeilen und Verwaltungszeilen, Varianten heutiger/alter Prompt × saubere/vergiftete Namensliste, Vorprobe gegen „verfügbar ohne Modell“, Bericht `AI-EVAL-REPORT-BEGIN/END`) über `scripts/run-ai-eval.sh [runtime]` (Sperren, Wegwerf-Simulator, Bericht nach `docs/artifacts/test-159-ai-eval/`); `SystemReceiptNameLanguageModel` ruft mit `GenerationOptions(sampling: .greedy)`. Nur lokal auf einem Mac mit Apple Intelligence; nicht in dieser Umgebung kompiliert. Details: `docs/specs/testing/test-159-ai-eval.md`.
- **`ReceiptTextRecognizer`** (Issue #120, `SmartCart/Services/ReceiptTextRecognizer.swift`) — die einzige Vision-Stelle für Bons; `ReceiptScannerView.process(_:)` und (seit der Fortsetzung von #120) `ShareViewController.process()` der Teilen-Erweiterung rufen ihn auf (Datei steht dafür auch in der Sources-Phase des Erweiterungsziels; Drift-Test in `ReceiptTextRecognizerTests`; Simulatornachweis `scripts/run-share-extension-uitest.sh`, 19 Positionen und 68,69 € auf iOS 26.5 und 27.0). Offene Grenze: Das Speicherlimit der Erweiterung (ca. 120 MB) wird im Simulator nicht erzwungen, am Gerät ist der Teilen-Weg erst nach Build 11 und Hennings Wort nachzuweisen. Details: `docs/specs/services/receipt-share-extension-recognizer.md`. Bilder mit Seitenverhältnis Höhe/Breite > 2,5 (z. B. digitale Lidl-Plus-Bons, 1206×9089 px) werden in überlappenden Streifen erkannt (Höhe 2×Breite, Überlappung 0,25×Breite), die Blöcke über `globalBox` in globale Koordinaten umgerechnet und Duplikate der Überlappung entfernt (`removingDuplicates`: gleicher Text, Mittelpunkt-Abstand < 0,5×Texthöhe); kleinere Bilder gehen unverändert in einem Durchgang (Original-CGImage, Original-Ausrichtung); gedrehte Bilder werden nur geschnitten, wenn das aufgerichtete Bild Streifen braucht. Ursache: Apples Texterkennung verliert bei sehr hohen Bildern im Einzelzug den Großteil des Textes (am echten Bon: Mac 4, Simulator 14, Gerät 3 Positionen, mit Streifen 18–19 samt Endsumme 68,69 €); `minimumTextHeight` und Revision 2 helfen nicht. Die Parameter sind an einem Bon gemessen. Offene Grenzen: Rabatte werden nicht je Artikel abgezogen (Produktfrage), Pfand im Streifenweg nicht zugeordnet, `RecipeRecognitionService` hat denselben Ganzbild-Aufruf (#123). Tests: `ReceiptTextRecognizerTests` (erzeugtes hohes Bon-Bild, Streifen-Mathematik, Testnaht `recognizeBlocks(imageSize:crop:recognize:)`). Details: `docs/specs/services/receipt-text-recognizer-tiling.md`.
- **`ReceiptResolutionStats`** (Issue #14, `SmartCart/Services/ReceiptResolutionStats.swift`) — local counter (app group) for how receipt lines were resolved, per stage: `ReceiptResolutionStage` (alias, dictionary, completed, history, ai, rawText, nonProduct), set as the optional `stage` on `ResolvedReceiptLine` by `ReceiptResolutionService`. It stores only stage keys and integers, never a line name; `ReceiptScannerView.save()` counts once per save. Shown in the dev screen `ReceiptResolutionStatsView` (Settings → Developer → „Bon-Auflösung“, below „Nachkauf-Statistik“, reset via alert). UI tests clean the counter with the DEBUG launch argument `-clearReceiptResolutionStatsForUITests`. Details: `docs/specs/services/receipt-resolution-stats.md`.
- **`NotificationService`** — schedules local replenishment notifications. Since Issue #30 C3 at most one bundled notification per day at 9:00 (`ReplenishmentDigestPlanner` in `SmartCart/Services/ReplenishmentDigest.swift`, 7 days ahead; overdue items go into the next digest instead of an immediate push). `HabitService.notificationCandidates` supplies the items (banner filters without the time window). An item enters `OverdueNotificationLedger` only after its digest's delivery time has passed (`ReplenishmentDigestLog.commitDelivered`), keyed by `ConsumptionPattern.notificationKey` (the purchase cycle, or the stored snooze date after „Hab noch“). `ReplenishmentBackgroundRefresh` re-plans via `BGAppRefreshTask` (`.backgroundTask(.appRefresh)` in `SmartCartApp`, identifier in `BGTaskSchedulerPermittedIdentifiers`, background mode `fetch`) so it works without opening the app.
- **`SharedStoreService`** (Issue #121) — geteilte Läden laufen NICHT über CKShare, sondern über einen Eigenbau auf der öffentlichen CloudKit-Datenbank: ein Record `SharedStore` je Laden, Abgleich per `modificationDate` gegen `lastSync_<code>`. TestFlight/App Store nutzen die **Produktionsumgebung**: Neue Felder des Records werden dort nicht automatisch angelegt, das Schema muss im CloudKit-Dashboard veröffentlicht werden (Schritt in `docs/testflight-setup.md`, vor dem Hochladen prüfen); sonst lehnt CloudKit jedes Speichern ab („Cannot create or modify field … in production schema“, Ursache von #121 seit Build 9 — Verdacht, Dashboard noch nicht eingesehen). `SharedStoreDatabase` (Protokoll vor der Datenbank) macht `syncToCloud` mit einem Fake testbar (`SharedStoreSchemaTests`, Fake-Produktion; Drift-Test der Feldliste). Bei Ablehnung wegen Produktions-Schema speichert `syncToCloud` genau einmal erneut ohne die optionalen Felder `categoriesJSON`/`assignmentsJSON` (`SharedStoreSchema.optionalExtensionFields`, Record frisch aufgebaut, nie `= nil` auf demselben Record). `SyncCoordinator.lastFailureKind` (jetzt Optional) kennt `.schemaIncomplete`, den nur ein vollständiger Push löscht (nie ein Pull); `lastFailureDetail` hält Domain/Code/Text. `SyncBanner.decision` und `SyncLog.message` sind reine Funktionen, `os.Logger` Kategorie `sync` (Fehlertext `.private`). Offene Grenze: echtes Speichern gegen CloudKit-Produktion ist nicht automatisiert prüfbar. Details: `docs/specs/services/shared-store-schema-fallback.md`.

### Views

**`HomeView`** is the main screen. It composes: header card, quick-add bar, replenishment banner, seasonal suggestions banner, an `UnassignedItemsCard` while items without a store exist (opens `UnassignedItemsSheet`: per-item suggestion with reason, one tap assigns and remembers via `StoreAssignmentOverrideService`, „Alle Vorschläge übernehmen“), store grid. While typing, the quick-add bar shows a `QuickAddTargetCard` (parsed quantity/name, target store, reason sentence, store chips that override the automatic choice before adding; a deviating choice is remembered as a correction). After adding, `QuickAddConfirmationToast` stays 6 s with „Laden ändern“ and „Rückgängig“. The views live in `SmartCart/Views/Home/QuickAddTargetViews.swift`. Toolbar: gear (Settings), fork.knife (MenuPlan), plus (AddItem). Bon-Übergabe aus der Teilen-Erweiterung: `checkPendingReceiptScan()` läuft in `onAppear`, bei `scenePhase == .active`, bei `restock://receiptscan` und seit Issue #35 zusätzlich, sobald `activeStores` von leer auf gefüllt wechselt (`.onChange(of: activeStores.isEmpty)`): Beim ersten Start nach Neuinstallation ist die `@Query` in `onAppear` unter Last noch leer, der Aufruf bricht bewusst vor `ReceiptShareHandoff.takePending()` ab (Nutzlast bleibt erhalten), und ohne den Nachversuch erschien der Prüf-Screen erst beim nächsten Öffnen. Details: `docs/specs/fast/fix-35-bon-pruefscreen-erster-start.md`.

**`StoreDetailView`** shows pending and completed items for one store. Sorting is chosen per store in the ··· menu (`Store.sortMode`: Einkaufsweg / Kategorie / Hinzugefügt, Issue #79). The route is learned per device from check-off order (`SmartCart/Models/ShoppingRoute.swift`: a check-off session persisted in the app group, ended after 30 min without a check-off, normalized positions 0…1, moving average α = 0.3, bulk check-offs at home ignored; never-seen items take their category's mean position in that store; category sections follow the learned category order). `Store.itemOrderMap` is legacy and no longer read. Details: `docs/specs/models/shopping-route-order.md`. Store-specific custom categories (Issue #85): created from the item dialogs via `CategoryPickerView` (search-or-create), stored on `Store` (`customCategoryEmojis`/`customCategoryDates`, logic in `SmartCart/Models/StoreCategories.swift`), remembered per item name (`categoryAssignments`, applied in `ShoppingItem.init`) and synced for shared stores as `categoriesJSON`; the remembered assignments are shared too (`assignmentsJSON`, per-key dates in `categoryAssignmentDates`, later wins incl. forgetting — Issue #94). A trip idle > 30 min is also finalized when the app returns to the foreground with the store list open (Issue #94). ··· → „Reihenfolge anpassen“ (Issue #86) drags items (route mode) or whole sections (category mode); `ShoppingRoute.applyManualOrder`/`applyManualCategoryOrder` write positions as a starting value and learning continues. Details: `docs/specs/models/store-custom-categories-and-manual-order.md`. In developer mode it also shows „Vielleicht auch fällig“ (Issue #30, C4, see `HabitService`). Live Activity (Dynamic Island, PO 2026-10-22): startet erst beim ersten Haken in einer Liste, nie beim Öffnen; bleibt beim Verlassen von Liste und App stehen; endet bei „alles erledigt“, nach 30 min ohne Haken (`LiveActivityPolicy.idleLimit` = `ShoppingRoute.tripGap`, geprüft beim Öffnen der Liste und beim Zurückkehren in die App über das `staleDate`) oder wenn in einem anderen Laden abgehakt wird (nur eine zugleich). Regel als reine Funktion `LiveActivityPolicy.action`, Ansichten rufen nur `LiveActivityService.handle(_:for:)`. Tests: `RestockTests/LiveActivityPolicyTests.swift` (P1–P12 Regel, I1–I3 echtes ActivityKit im Simulator). Offene Grenzen: Läuft die App nach 30 min nicht, bleibt die Anzeige als veraltet stehen, bis iOS sie nach spätestens 8 h beendet; `AppIntentsUITests` T2 (nur lokal) setzt noch den Start beim Öffnen voraus.

**`ReceiptReviewCard`** (`SmartCart/Views/Prices/ReceiptReviewCard.swift`) renders each parsed receipt line in `ReceiptScannerView`'s review list as its own card: the printed receipt text (15pt, `Color.ink`, copyable via `.contextMenu`), up to three selectable name options (best list matches, AI suggestion, the current name) plus an always-visible text field as the last row, pre-filled with the receipt text capitalized word by word (`customFieldSeed`; selecting the row or typing in it makes the text the line's name, clearing it falls back to the previous selection — the former „wie auf dem Bon“ row of Issue #65 is gone), a price/quantity summary line, and an inline "Ändern" editor for price and quantity. Replaces the former single-row `ReceiptLineRow`. The marking rule (`isSelected`) is a static, unit-testable function `isSelected(_:for:customActive:)` since Issue #66; an AI-resolved name also marks the name-matching list option even without an existing `matchedItemID` link.

**`SettingsView`** handles: country/language pickers, store setup, notification toggles, version tap (5× to unlock dev mode), dev section (Feedback + Todos).

### Developer mode

Activated by tapping the version number 5× in Settings → password sheet (SHA256-hashed). Password hash stored in `SettingsView.devPasswordHash`. Once active:

- Orange **DEV pill** appears top-right (counts open `FeedbackItem`s via `@Query`; tap → `FeedbackListView`).
- Every screen shows a red **thumbs-down button** (bottom-right) via the `.devFeedback(context:)` view modifier — opens `DevFeedbackSheet` which saves a `FeedbackItem` via `modelContext`.
- Settings dev section exposes `FeedbackListView` and `TodoListView`.

**`FeedbackListView`**: two segmented pickers (Status + Priority), rows with inline priority segmented picker + green toggle for `isResolved`, swipe-to-delete, "Gelöste löschen" toolbar button.

**`TodoListView`**: Offen/Erledigt sections, tap row for notes, swipe actions (complete/delete/reopen), `+` toolbar button.

### Design conventions

- **Haptics**: always use `Haptics.impact(.light/.medium/.heavy)` or `Haptics.success()` — never `UIImpactFeedbackGenerator` directly.
- **Colors**: use semantic tokens from `DesignSystem.swift` (`Color.brand`, `.success`, `.warning`, `.destructive`) and `LinearGradient.brand`. `Color.amber` (`RCAmber`, Nachkauf-Dringlichkeit und „ca.“-Schätzungen) muss in beiden Modi WCAG 2.1 AA für Fließtext erreichen (≥ 4,5:1 gegen `RCSurface` und die weiße Karte); die Werte stehen in `AssignmentServiceQuantitySuggestionTests` (`testAmberDarkModeContrastMeetsWCAGAA`, `testAmberLightModeContrastMeetsWCAGAA`, Issue #75: Hellmodus 0,544/0,408/0,148 seit 2026-10-20, vorher 3,52:1). Sichtbare Farbänderungen brauchen vorher eine Entwurfsvorschau hell/dunkel mit Alternative (Regel vom 2026-09-22; Beispiel `docs/artifacts/fix-75-amber-kontrast/entwurfsvorschau.html`).
- **Card styling**: `.cardStyle()` view modifier gives white background + rounded corners + shadow.
- **Localization**: all user-facing strings via `String(localized: "key")`. Keys are defined in `Resources/`.
- **Dev feedback on every screen**: apply `.devFeedback(context: "Screen Name")` to the outermost view of every full-screen view. For `StoreDetailView`, include the store name: `.devFeedback(context: "Liste: \(store.name)")`.

### Siri / App Intents

`SmartCart/Intents/AddItemIntent.swift` — `AddShoppingItemIntent` creates its own `ModelContainer` (intents run out-of-process). Phrases must not contain `\(\.$parameter)` placeholders for `String` parameters (only `AppEntity`/`AppEnum` allowed); Siri will prompt for missing values via `requestValueDialog`.

### Barcode scanning

`BarcodeScannerSheet` wraps `DataScannerViewController` (VisionKit, iOS 16+). On barcode tap, calls Open Food Facts API (`world.openfoodfacts.org/api/v2/product/{barcode}`) for product name. Camera permission is already declared in the project settings.
